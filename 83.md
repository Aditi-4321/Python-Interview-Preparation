# Question 83 — Given an unfamiliar Python codebase, explain how you would debug and understand it.

## Answer

When working with an unfamiliar Python codebase, I would **understand the structure first, reproduce the problem, trace the execution flow, and then debug the specific component** rather than changing code randomly.

A practical workflow is:

```text
Understand project structure
        ↓
Set up the environment
        ↓
Find the entry point
        ↓
Reproduce the issue
        ↓
Trace execution flow
        ↓
Inspect variables and data
        ↓
Identify the root cause
        ↓
Make the smallest safe fix
        ↓
Run tests
        ↓
Verify the fix
```

## 1. Understand the Project Structure

First, I would inspect the files and directories.

For example:

```text
project/
│
├── app/
│   ├── main.py
│   ├── models.py
│   ├── services.py
│   └── utils.py
│
├── tests/
├── requirements.txt
├── README.md
└── .env.example
```

I would identify:

* Application entry point
* Main modules
* Configuration files
* Tests
* Dependency files
* Database/API integrations
* Documentation

I would read the **README** first if available because it often explains how the application is supposed to work.

---

## 2. Set Up the Environment

Before debugging, I would reproduce the project's environment.

For example:

```bash
python -m venv .venv
```

Activate the environment and install dependencies:

```bash
python -m pip install -r requirements.txt
```

I would also check the Python version:

```bash
python --version
```

and verify which interpreter is being used:

```bash
python -c "import sys; print(sys.executable)"
```

This is important because an issue can be caused by **Python-version or dependency differences**, not necessarily by the application code.

---

## 3. Find the Entry Point

Next, I would determine where execution starts.

Common examples include:

```python
if __name__ == "__main__":
    main()
```

or a web application such as:

```python
app = FastAPI()
```

or:

```python
app = Flask(__name__)
```

For an ML project, the entry point might be:

```text
train.py
predict.py
inference.py
pipeline.py
```

Understanding the entry point helps me trace:

```text
Input → Processing → Model → Output
```

---

## 4. Reproduce the Problem

I would first reproduce the issue consistently.

For example:

```text
Input:
customer_data.csv

Expected:
Prediction generated successfully

Actual:
ValueError: could not convert string to float
```

I would record:

* Exact error message
* Full traceback
* Input that causes the error
* Expected behavior
* Actual behavior
* Steps required to reproduce it

A reproducible bug is much easier to investigate.

---

## 5. Read the Traceback

Python tracebacks are extremely useful.

For example:

```text
Traceback (most recent call last):
  File "main.py", line 20, in <module>
    result = process_data(data)
  File "processor.py", line 15, in process_data
    value = float(row["age"])
ValueError: could not convert string to float: 'unknown'
```

I would start from the **bottom of the traceback**, where the exception type and message usually appear, and then trace upward to understand how execution reached that point.

Here the immediate problem is:

```python
float("unknown")
```

The next question is **why `"unknown"` reached this code** and whether the correct fix belongs in validation, preprocessing, or elsewhere.

---

## 6. Trace the Data Flow

In data-processing or ML projects, understanding **how data changes** is especially important.

For example:

```text
CSV
 ↓
Data loading
 ↓
Cleaning
 ↓
Feature engineering
 ↓
Encoding
 ↓
Scaling
 ↓
Model
 ↓
Prediction
```

I would inspect the data at important boundaries:

```python
print(data.shape)
print(data.dtypes)
print(data.head())
print(data.isnull().sum())
```

For normal Python objects:

```python
print(type(data))
print(data)
```

But I would avoid excessive printing in production code.

---

## 7. Use a Debugger

For complex problems, I would use a debugger rather than adding many `print()` statements.

Python provides `breakpoint()`:

```python
def process_data(data):
    cleaned_data = clean(data)

    breakpoint()

    result = transform(cleaned_data)
    return result
```

When execution reaches `breakpoint()`, I can inspect variables and execute commands interactively.

I can also use an IDE such as VS Code to:

* Set breakpoints
* Step over a line
* Step into a function
* Step out of a function
* Inspect variables
* Watch expressions
* Examine the call stack

This helps identify **where the actual state becomes incorrect**.

---

## 8. Check Dependencies and External Services

An unfamiliar codebase may depend on:

* Databases
* REST APIs
* Cloud services
* Environment variables
* File systems
* Model files
* API keys
* External packages

I would check configuration carefully.

For example:

```python
import os

print(os.getenv("DATABASE_URL"))
```

I would avoid printing secrets such as passwords or API keys.

For ML projects, I would also verify:

* Model file exists
* Model version is compatible
* Preprocessing matches training
* Required feature columns exist
* Dependency versions are compatible

---

## 9. Understand Before Changing

I would avoid immediately rewriting code.

For example, if I find:

```python
result = process(data)
```

I would first understand:

* What does `process()` expect?
* What does it return?
* Which functions does it call?
* Does it modify `data`?
* Which other modules depend on it?

This prevents fixing one problem while introducing another.

---

## 10. Make the Smallest Safe Fix

Once the root cause is identified, I would make the smallest change that solves the problem.

For example, if the problem is invalid input:

```python
def parse_age(value):
    if not value.isdigit():
        raise ValueError("Age must be numeric")

    return int(value)
```

The goal is not simply:

> "Make the error disappear."

The goal is:

> **Fix the underlying cause while preserving expected behavior.**

---

## 11. Run Tests

After making the change, I would run the existing test suite.

For example:

```bash
pytest
```

I would test:

* Original failing case
* Normal/valid input
* Edge cases
* Related functionality

If a regression test does not exist, I would add one when appropriate.

For example:

```python
def test_invalid_age():
    with pytest.raises(ValueError):
        parse_age("unknown")
```

---

## 12. Review the Fix

Finally, I would check:

* Is the root cause actually fixed?
* Did the change break another feature?
* Is the code readable?
* Are error messages useful?
* Are tests passing?
* Did performance or memory usage change?
* Are logs sufficient for future debugging?

For production systems, I would also consider monitoring and rollback if the change is deployed.

---

## Example Debugging Scenario

Suppose an ML API returns an error:

```text
ValueError: X has 8 features, but model expects 10 features
```

I would investigate systematically:

```text
API request
    ↓
Input validation
    ↓
Feature extraction
    ↓
Preprocessing
    ↓
Model input
    ↓
Prediction
```

I would check:

```python
print(X.shape)
print(model.n_features_in_)
```

Then determine whether:

* Two features were missing.
* Feature engineering changed.
* Training and inference pipelines differ.
* Columns are being selected incorrectly.
* The wrong model version was loaded.

I would fix the root cause rather than simply padding the input with dummy values.

## Useful Debugging Tools

| Tool             | Purpose                               |
| ---------------- | ------------------------------------- |
| `print()`        | Quick inspection                      |
| `breakpoint()`   | Interactive debugging                 |
| VS Code debugger | Breakpoints and call-stack inspection |
| `pdb`            | Python debugger                       |
| `logging`        | Application/runtime diagnostics       |
| `pytest`         | Automated testing                     |
| `cProfile`       | Performance profiling                 |
| `tracemalloc`    | Python memory allocation tracking     |
| `ruff`/linters   | Detect code-quality issues            |
| Type checkers    | Detect certain type-related problems  |

## Common Mistakes

* Changing code before reproducing the problem.
* Ignoring the traceback.
* Debugging only the final error instead of tracing the data flow.
* Assuming the error is always in the line where it appears.
* Ignoring dependency or environment differences.
* Using excessive `print()` statements instead of a debugger or logging.
* Fixing symptoms without identifying the root cause.
* Not adding a regression test after fixing an important bug.
* Printing passwords, API keys, tokens, or other sensitive information while debugging.

### Interview Follow-up

**Q: What is the difference between debugging and logging?**

> Debugging is the process of investigating and identifying the cause of a problem. Logging is a mechanism for recording useful runtime information so that application behavior and failures can be understood, especially in environments where interactive debugging is not possible.

**Q: What would you do if you cannot reproduce the bug locally?**

> I would collect the exact traceback, logs, input/context, environment and dependency versions, then compare the failing environment with mine. I would also add targeted diagnostic logging or monitoring and look for differences in data, configuration, timing, or external services.

### Interview Takeaway

> When given an unfamiliar Python codebase, **understand the architecture, set up the correct environment, reproduce the issue, read the traceback, trace data and control flow, use a debugger, identify the root cause, make a minimal fix, and verify it with tests**.
