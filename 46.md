# Question 46 — How do you create and raise custom exceptions?

## Answer

A **custom exception** is a user-defined exception created for application-specific errors that are not clearly represented by Python's built-in exceptions.

Custom exceptions make error handling more **meaningful, readable, and maintainable**, especially in larger applications and ML/data-processing pipelines.

### 1. Creating a Custom Exception

A custom exception is usually created by defining a class that inherits from Python's `Exception` class.

```python
class InvalidAgeError(Exception):
    pass
```

Here, `InvalidAgeError` is a custom exception.

---

### 2. Raising a Custom Exception

The `raise` statement is used to explicitly generate an exception.

```python
class InvalidAgeError(Exception):
    pass


age = 15

if age < 18:
    raise InvalidAgeError("Age must be at least 18.")
```

Output:

```text
InvalidAgeError: Age must be at least 18.
```

The exception can then be handled using `try` and `except`:

```python
class InvalidAgeError(Exception):
    pass


try:
    age = 15

    if age < 18:
        raise InvalidAgeError("Age must be at least 18.")

except InvalidAgeError as e:
    print("Error:", e)
```

Output:

```text
Error: Age must be at least 18.
```

### 3. Why Create Custom Exceptions?

Built-in exceptions such as `ValueError`, `TypeError`, and `FileNotFoundError` are useful for common errors. However, an application may have **domain-specific errors**.

For example:

* `InvalidAgeError`
* `InsufficientBalanceError`
* `InvalidModelInputError`
* `DataValidationError`
* `ModelNotFoundError`

This allows the calling code to handle different application errors separately.

```python
class DataValidationError(Exception):
    pass


def validate_data(data):
    if not data:
        raise DataValidationError("Input dataset is empty.")


try:
    validate_data([])

except DataValidationError as e:
    print("Validation failed:", e)
```

### 4. Custom Exception with Additional Information

A custom exception can also store additional information.

```python
class InvalidScoreError(Exception):
    def __init__(self, score):
        self.score = score
        super().__init__(f"Invalid score: {score}. Score must be between 0 and 100.")


try:
    score = 120

    if score < 0 or score > 100:
        raise InvalidScoreError(score)

except InvalidScoreError as e:
    print(e)
    print("Invalid value:", e.score)
```

This is useful when the caller needs structured information about the error, not just an error message.

### 5. Custom Exceptions in ML Projects

Custom exceptions are useful for making ML pipelines easier to debug and maintain.

For example:

```python
class InvalidModelInputError(Exception):
    pass


def predict(features):
    if len(features) != 10:
        raise InvalidModelInputError(
            "Model requires exactly 10 features."
        )

    # prediction logic


try:
    predict([1, 2, 3])

except InvalidModelInputError as e:
    print("Prediction error:", e)
```

Instead of receiving a generic error, the application gets a specific exception that clearly describes the problem.

### 6. Exception Hierarchy

Custom exceptions can also form a hierarchy.

```python
class MLApplicationError(Exception):
    pass


class DataValidationError(MLApplicationError):
    pass


class ModelLoadError(MLApplicationError):
    pass
```

Now we can handle all application-specific ML errors together:

```python
try:
    # ML operation
    raise DataValidationError("Invalid dataset.")

except MLApplicationError as e:
    print("ML error:", e)
```

Or handle a specific error:

```python
try:
    raise DataValidationError("Invalid dataset.")

except DataValidationError as e:
    print("Data error:", e)
```

This hierarchy is useful in larger applications because different levels of errors can be handled at different layers.

### Common Mistakes

* Creating a custom exception without inheriting from `Exception` or an appropriate exception class.
* Raising a generic `Exception` when a meaningful domain-specific exception would be clearer.
* Catching every exception using a broad `except Exception:` without proper handling or logging.
* Using exceptions for normal program flow instead of actual exceptional conditions.
* Losing the original error when converting exceptions; when wrapping an underlying error, use exception chaining:

```python
try:
    load_model()
except FileNotFoundError as e:
    raise ModelLoadError("Model file could not be loaded.") from e
```

Here, `from e` preserves the relationship with the original exception and makes debugging easier.

### Interview Takeaway

> **A custom exception is created by defining a class that inherits from `Exception` (or another appropriate exception), and it is explicitly raised using the `raise` statement. Custom exceptions make application-specific errors clearer, easier to catch, and easier to maintain.**

### Interview Follow-up

**Q: What is the difference between `raise` and `raise ... from`?**

* `raise` explicitly raises an exception.
* `raise ... from e` raises a new exception while preserving the original exception as its cause, which is useful for exception chaining and debugging.
