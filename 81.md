# Question 81 — Debug a memory-heavy Python program.

## Answer

A memory-heavy Python program consumes more memory than expected, which can lead to **slow performance, swapping, out-of-memory errors, or process termination**.

The correct approach is to **measure memory usage first, identify what is consuming memory, and then optimize the actual bottleneck**.

### Example of a memory-heavy program

Suppose we want to process a very large file:

```python
def read_file(filename):
    with open(filename, "r", encoding="utf-8") as f:
        data = f.readlines()

    return data


data = read_file("large_data.txt")

for line in data:
    process(line)
```

The problem is:

```python
data = f.readlines()
```

`readlines()` loads the **entire file into memory**.

If the file is several GB in size, memory consumption can become very large.

---

## Step 1: Process the file lazily

Instead of loading everything at once:

```python
def read_file(filename):
    with open(filename, "r", encoding="utf-8") as f:
        for line in f:
            yield line


for line in read_file("large_data.txt"):
    process(line)
```

Now only the current line needs to be processed.

This uses a **generator/file iterator**, making memory usage much smaller.

### Why this works

The original approach is approximately:

```text
Entire file
     ↓
Memory
```

The generator approach is:

```text
File → one line → process → next line → process → ...
```

This is a common pattern for large datasets and ML preprocessing.

---

# Step 2: Measure memory usage

Do not optimize based only on assumptions.

Python's `tracemalloc` can track Python-level memory allocations:

```python
import tracemalloc

tracemalloc.start()

# Code being investigated
data = [x * 2 for x in range(1000000)]

current, peak = tracemalloc.get_traced_memory()

print("Current:", current / 1024 / 1024, "MB")
print("Peak:", peak / 1024 / 1024, "MB")

tracemalloc.stop()
```

This helps identify how much Python-managed memory is currently allocated and the peak observed during tracing.

For more detailed investigation:

```python
snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics("lineno")

for stat in top_stats[:10]:
    print(stat)
```

This can show which lines are responsible for significant allocations.

---

# Step 3: Look for common causes

### 1. Loading the entire dataset

Problem:

```python
data = list(range(10000000))
```

Better:

```python
def generate_data():
    for x in range(10000000):
        yield x
```

Use generators when sequential, lazy processing is sufficient.

---

### 2. Creating unnecessary copies

Problem:

```python
new_data = old_data.copy()
```

If `old_data` is very large, this creates another large container.

Before copying, ask:

> Do I really need an independent copy?

For large numerical data, also check whether operations create temporary arrays.

---

### 3. Keeping unnecessary references

For example:

```python
results = []

for data in large_dataset:
    result = process(data)
    results.append(result)
```

If every result is stored but no longer needed, memory keeps increasing.

Instead, process results incrementally:

```python
for data in large_dataset:
    result = process(data)
    save_result(result)
```

---

### 4. Growing caches or global collections

A cache that never removes old entries can continuously consume memory:

```python
cache = {}

def get_data(key):
    result = expensive_operation(key)
    cache[key] = result
    return result
```

If there are millions of unique keys, the cache can become very large.

Use an appropriate eviction strategy or bounded cache when possible.

For example:

```python
from functools import lru_cache

@lru_cache(maxsize=1000)
def get_data(key):
    return expensive_operation(key)
```

---

# Step 4: Check whether objects are actually released

Python uses automatic memory management, but objects remain alive while references to them exist.

For example:

```python
data = load_large_data()

process(data)

del data
```

`del` removes the reference held by `data`. If no other references remain, the object can become eligible for reclamation.

However, deleting a Python object does **not guarantee that the operating system immediately receives the memory back**. Python's allocator may retain memory for reuse within the process.

---

# Step 5: Use appropriate data structures

Data structure choice can have a significant memory impact.

For example, if you only need unique values:

```python
values = list(set(values))
```

may not be the best approach if the list itself is already huge and unnecessary.

Instead, consider whether the data needs to remain materialized at all.

For numerical workloads, NumPy arrays can often use memory more efficiently than Python lists because they store homogeneous values in compact array storage:

```python
import numpy as np

data = np.array([1, 2, 3, 4], dtype=np.int32)
```

The appropriate dtype matters too:

```python
np.int32
```

uses less storage per element than:

```python
np.int64
```

when the smaller range is sufficient.

---

# Step 6: Process large ML datasets in batches

Instead of:

```python
data = load_entire_dataset()

model.predict(data)
```

process the data in batches:

```python
for batch in load_batches():
    predictions = model.predict(batch)
    save_predictions(predictions)
```

This limits peak memory usage and is particularly useful when working with:

* Large datasets
* Images
* Embeddings
* Large DataFrames
* Model inference
* GPU workloads

For ML systems, remember that memory may exist in several places: **Python RAM, NumPy/native allocations, and GPU memory**. `tracemalloc` primarily tracks Python-level allocations, so it is not a complete GPU/native-memory profiler.

---

# Step 7: Debug memory leaks

A memory leak-like problem can occur when objects remain referenced unintentionally.

Useful tools include:

* `tracemalloc` — Python allocation tracking
* `gc` — inspect/control cyclic garbage collection
* `sys.getsizeof()` — shallow size of an object
* `memory_profiler` — line-level memory profiling when available
* OS/container metrics — process RSS and overall memory
* Framework-specific profilers — useful for NumPy/PyTorch/GPU memory

For example:

```python
import tracemalloc

tracemalloc.start()

# Run suspicious code here

snapshot = tracemalloc.take_snapshot()

for stat in snapshot.statistics("lineno")[:10]:
    print(stat)

tracemalloc.stop()
```

### Important distinction

`sys.getsizeof()` only reports the object's **shallow size**. It does not automatically calculate the complete memory footprint of every nested object referenced by that object.

# Practical Debugging Workflow

When a Python program becomes memory-heavy:

```text
Measure
   ↓
Find the memory-consuming operation
   ↓
Check for unnecessary copies/references
   ↓
Stream or batch the data
   ↓
Choose efficient data structures/dtypes
   ↓
Control caches
   ↓
Re-measure peak memory
   ↓
Verify correctness and performance
```

The key is to optimize **peak memory usage**, not just the final memory usage.

### Example: Before and After

**Memory-heavy:**

```python
def process_file(filename):
    with open(filename, "r", encoding="utf-8") as f:
        lines = f.readlines()

    return [line.strip() for line in lines]
```

**More memory-efficient:**

```python
def process_file(filename):
    with open(filename, "r", encoding="utf-8") as f:
        for line in f:
            yield line.strip()


for line in process_file("large_data.txt"):
    process(line)
```

The second version avoids creating a list containing the entire file and all processed strings.

### Complexity

For `n` input records:

* **Time:** generally O(n), depending on `process()`
* **Memory-heavy version:** O(n) additional memory
* **Generator version:** approximately O(1) additional memory for the iteration itself, excluding the current item and any memory retained by downstream processing

### Common Mistakes

* Calling `list()` on a generator unnecessarily.
* Loading an entire large file or dataset into memory.
* Creating unnecessary copies of large objects.
* Keeping results in lists when they can be processed incrementally.
* Assuming `del` always returns memory immediately to the OS.
* Using `tracemalloc` as if it measures all native or GPU memory.
* Optimizing before measuring the actual memory bottleneck.

### Interview Follow-up

**Q: What would you use to find where Python memory is being allocated?**

> I would start with `tracemalloc` for Python-level allocations, compare current and peak memory, inspect allocation statistics, and then use framework/OS-specific tools if the memory is coming from native libraries or GPU memory.

**Q: How would you reduce memory usage when processing a huge dataset?**

> I would avoid loading the entire dataset, use streaming or generators, process data in batches, select only required columns, use appropriate data types, avoid unnecessary copies, and measure peak memory before and after optimization.

### Interview Takeaway

> When debugging a memory-heavy Python program, **measure first, identify unnecessary allocations or retained references, then reduce peak memory through streaming, batching, efficient data structures, and controlled object lifetimes**.
