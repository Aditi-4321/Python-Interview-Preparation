# Question 66 — Threading vs multiprocessing — what is the difference?

## Answer

**Threading** and **multiprocessing** are two ways to execute multiple tasks concurrently in Python, but they differ mainly in whether tasks run within the **same process** or in **separate processes**.

The most important distinction is:

> **Threading uses multiple threads within one process, while multiprocessing uses multiple processes, each with its own Python interpreter and memory space.**

---

## 1. Threading

A **thread** is a lightweight unit of execution inside a process.

Multiple threads within the same process generally share the process's memory.

```text
Process
│
├── Thread 1
├── Thread 2
└── Thread 3
```

Example:

```python id="1j5f8h"
import threading

def work(name):
    print(f"Working on {name}")

t1 = threading.Thread(target=work, args=("Task 1",))
t2 = threading.Thread(target=work, args=("Task 2",))

t1.start()
t2.start()

t1.join()
t2.join()
```

### Advantages

* Lightweight compared with processes
* Threads share memory
* Communication between threads can be relatively easy
* Useful for I/O-bound tasks

### Disadvantages

* Shared memory can cause race conditions
* Synchronization may be required
* Traditional GIL-enabled CPython limits simultaneous execution of Python bytecode across threads
* Debugging concurrent code can be difficult

---

# 2. Multiprocessing

**Multiprocessing** creates multiple independent processes.

Each process has its own Python interpreter and memory space.

```text
Process 1 → Memory 1
Process 2 → Memory 2
Process 3 → Memory 3
```

Example:

```python id="r4z4qo"
from multiprocessing import Process

def work(name):
    print(f"Working on {name}")

p1 = Process(target=work, args=("Task 1",))
p2 = Process(target=work, args=("Task 2",))

p1.start()
p2.start()

p1.join()
p2.join()
```

Because processes are independent, suitable CPU-bound tasks can execute in parallel on multiple CPU cores.

### Advantages

* Can achieve true CPU parallelism for suitable workloads
* Not restricted by the traditional per-process GIL in the same way as threads
* Process memory is isolated
* A failure in one process is generally more isolated from another process

### Disadvantages

* Higher memory usage
* Process creation has more overhead
* Communication between processes is more expensive
* Data often needs to be serialized when passed between processes
* Managing processes is more complex

---

# 3. Main Difference

| Feature               | Threading                             | Multiprocessing                       |
| --------------------- | ------------------------------------- | ------------------------------------- |
| Basic unit            | Thread                                | Process                               |
| Number of processes   | Usually one                           | Multiple                              |
| Memory                | Shared within process                 | Separate                              |
| Creation overhead     | Lower                                 | Higher                                |
| Communication         | Relatively easy through shared memory | More expensive; IPC mechanisms needed |
| CPU-bound Python code | Limited by traditional CPython GIL    | Can use multiple CPU cores            |
| I/O-bound tasks       | Very suitable                         | Can be used, but often unnecessary    |
| Memory usage          | Usually lower                         | Usually higher                        |
| Isolation             | Lower                                 | Higher                                |
| Common Python module  | `threading`                           | `multiprocessing`                     |

---

# 4. When should you use Threading?

Threading is often appropriate for **I/O-bound tasks**.

Examples:

* Downloading files
* Calling APIs
* Database requests
* Reading/writing files
* Network communication

Suppose you need to download 100 files.

Sequential execution:

```text
Download 1 → wait
Download 2 → wait
Download 3 → wait
...
```

With threads:

```text
Thread 1 → Download
Thread 2 → Download
Thread 3 → Download
Thread 4 → Download
```

While one thread waits for I/O, another thread can make progress.

This can improve overall throughput.

---

# 5. When should you use Multiprocessing?

Multiprocessing is often appropriate for **CPU-bound tasks**.

Examples:

* CPU-heavy calculations
* Image processing
* Large numerical computations
* CPU-intensive data transformations
* Some scientific computations

For example:

```text
Large dataset
      ↓
Split into chunks
      ↓
Process 1 → Chunk 1
Process 2 → Chunk 2
Process 3 → Chunk 3
Process 4 → Chunk 4
      ↓
Combine results
```

This can use multiple CPU cores.

However, multiprocessing is not automatically faster. If each task is very small, process creation and communication overhead can outweigh the benefit.

---

# 6. Why does the GIL matter?

In traditional GIL-enabled CPython, only one thread at a time can execute Python bytecode within a process.

Therefore, for CPU-heavy Python code:

```text
Thread 1 ──┐
Thread 2 ──┼──> Same CPython process
Thread 3 ──┘
             ↓
       Traditional GIL
```

Threads can still be useful for I/O, because a thread may release execution opportunities while waiting for I/O.

With multiprocessing:

```text
Process 1 → GIL 1 → CPU Core 1
Process 2 → GIL 2 → CPU Core 2
Process 3 → GIL 3 → CPU Core 3
```

Each process has its own interpreter state, so suitable CPU-bound work can run in parallel across cores.

**Important:** Modern CPython also supports optional free-threaded builds, so the traditional GIL limitation is not universal across every current CPython build.

---

# 7. Shared Memory vs Separate Memory

This is one of the most important conceptual differences.

### Threading

Threads normally share the same process memory:

```text
             Process
          /     |     \
     Thread 1 Thread 2 Thread 3
          \     |     /
          Shared memory
```

Therefore:

```python id="yqg8c5"
data = []

# Multiple threads can access data
```

This makes communication easier but introduces synchronization problems.

For example, two threads modifying shared state simultaneously can cause a **race condition**.

Tools such as:

```python id="4p3s7k"
threading.Lock()
```

can help protect shared resources.

### Multiprocessing

Processes normally have separate memory:

```text
Process 1 → Memory 1

Process 2 → Memory 2

Process 3 → Memory 3
```

If processes need to communicate, Python provides mechanisms such as:

* `Queue`
* `Pipe`
* Shared memory
* Manager objects

But communication usually has more overhead than accessing shared memory between threads.

---

# 8. Example: I/O-bound vs CPU-bound

### I/O-bound

Suppose an application calls 50 APIs.

```text
Best candidate → Threading / asyncio
```

because much of the time is spent waiting for network responses.

### CPU-bound

Suppose an application needs to process millions of computationally expensive records.

```text
Best candidate → Multiprocessing / optimized native code
```

depending on the workload.

---

# 9. AI/ML Perspective

The choice matters frequently in AI/ML systems.

### Data downloading

Suppose you need to download training images:

```text
Network I/O
     ↓
Threading / asyncio
```

can be useful.

### CPU preprocessing

Suppose each image requires expensive CPU preprocessing:

```text
Images
   ↓
Process 1 → Batch 1
Process 2 → Batch 2
Process 3 → Batch 3
```

Multiprocessing may be appropriate.

### Numerical computation

For NumPy/PyTorch workloads, first check whether the library already performs the computation efficiently using native code, multithreading, or GPU acceleration.

Don't automatically add Python threads or processes.

---

# 10. Threading vs Multiprocessing vs Asyncio

These are often confused.

| Approach                       | Best suited for                              |
| ------------------------------ | -------------------------------------------- |
| `threading`                    | I/O-bound work using threads                 |
| `multiprocessing`              | CPU-bound parallel work                      |
| `asyncio`                      | Large numbers of cooperative I/O-bound tasks |
| Vectorization/native libraries | Numerical CPU workloads                      |
| GPU frameworks                 | Highly parallel ML/numerical workloads       |

`asyncio` does not automatically make CPU-bound code parallel. It is primarily a concurrency model for I/O-bound operations.

---

# 11. Simple Decision Rule

A useful interview rule is:

```text
Is the task CPU-bound?
        │
      Yes
        ↓
Multiprocessing / native optimized code
        │
      No
        ↓
Is it I/O-bound?
        │
      Yes
        ↓
Threading / asyncio
```

But in real systems, profile first because the actual bottleneck and library behavior matter.

---

## Common Mistakes

* ❌ Saying threading is always faster than multiprocessing.
* ❌ Saying multiprocessing is always better for CPU-bound tasks without considering overhead.
* ❌ Saying threads cannot run concurrently.
* ❌ Saying the GIL prevents all threading.
* ❌ Assuming `asyncio` provides CPU parallelism.
* ❌ Ignoring shared-state and synchronization problems.
* ❌ Creating processes for very small tasks where overhead dominates.
* ❌ Adding concurrency before profiling the application.

## Interview Follow-up

**Q: Why are threads useful despite the GIL?**

> Because I/O-bound threads can make progress while other threads are waiting for I/O. The GIL mainly limits simultaneous execution of Python bytecode, not the usefulness of concurrency for I/O.

**Q: Why can multiprocessing achieve CPU parallelism?**

> Separate processes have separate interpreter states and can run on different CPU cores.

**Q: Which uses more memory?**

> Multiprocessing generally uses more memory because processes have separate memory spaces, although the exact behavior depends on the operating system and how memory is shared.

## Interview Takeaway

> **Threading uses multiple threads within the same process and is commonly useful for I/O-bound tasks. Multiprocessing uses separate processes with separate memory spaces and is commonly useful for CPU-bound parallel workloads. In traditional GIL-enabled CPython, threads are limited for CPU-bound Python bytecode, while multiprocessing can use multiple CPU cores.**
