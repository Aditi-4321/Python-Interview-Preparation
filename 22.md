# Question 22 — Why must dictionary keys be hashable?

## Answer

Dictionary keys must be **hashable** because Python dictionaries use a **hash-table-based structure** to store and find key-value pairs efficiently.

A hashable object has:

1. A hash value that can be obtained using `hash()`.
2. Equality behavior that is consistent with its hash value.
3. A hash value that remains stable during its lifetime as a key.

For example:

```python
d = {
    "name": "Aditi",
    101: "MCA"
}
```

Both `"name"` and `101` are hashable, so they can be used as dictionary keys.

---

## 1. What Does Hashable Mean?

An object is **hashable** if it has a hash value that can be used by Python's hash-table-based data structures.

You can check this using:

```python
print(hash("Python"))
print(hash(100))
```

These objects can therefore be used as keys:

```python
data = {
    "Python": 1,
    100: 2
}
```

---

## 2. Why Does a Dictionary Need Hashing?

Suppose we have:

```python
student = {
    "name": "Aditi",
    "age": 21,
    "course": "MCA"
}
```

When we execute:

```python
student["course"]
```

Python conceptually performs:

```text
"course"
    ↓
hash("course")
    ↓
hash value
    ↓
find appropriate table location
    ↓
check key
    ↓
return "MCA"
```

This allows dictionary lookup to be **O(1) on average** instead of searching through every key.

So hashing is fundamental to how dictionaries efficiently locate entries.

---

## 3. Why Can't a List Be a Key?

Consider:

```python
data = {
    [1, 2, 3]: "value"
}
```

This produces:

```text
TypeError: unhashable type: 'list'
```

The reason is that a list is **mutable**.

For example:

```python
x = [1, 2, 3]
```

Later:

```python
x.append(4)
```

The contents of the list have changed.

If a mutable object were used as a dictionary key and its contents changed in a way that affected its hash, Python could have difficulty locating the entry in the hash table.

Conceptually:

```text
Before:
key = [1, 2, 3]
hash → location A

After modification:
key = [1, 2, 3, 4]
hash → potentially different location
```

The dictionary could have stored the key at the old location but then search for it at a different location.

Therefore, dictionary keys need a **stable hash**.

---

## 4. Why Are Strings Valid Keys?

Strings are immutable:

```python
name = "Aditi"
```

You cannot modify the existing string in place.

For example:

```python
name[0] = "B"
```

raises an error.

Instead, operations that appear to modify a string create a new string:

```python
name = name.upper()
```

Because the string's value does not change in place, its hash remains stable while it is used as a dictionary key.

---

## 5. What About Tuples?

Tuples are immutable:

```python
point = (10, 20)

data = {
    point: "location"
}
```

This works because the tuple can be hashable.

However, an important condition is:

> **All elements inside the tuple must be hashable.**

For example:

```python
data = {
    (10, 20): "Point A"
}
```

works.

But:

```python
data = {
    ([10, 20], 30): "Point A"
}
```

does not work because the tuple contains a list, and the list is unhashable.

So:

```text
Tuple
 ├── int       → hashable
 └── int       → hashable
       ↓
    Tuple is hashable
```

But:

```text
Tuple
 ├── list      → unhashable
 └── int
       ↓
    Tuple is unhashable
```

---

## 6. Hashability and Equality Must Agree

There is an important rule:

> If `a == b` is `True`, then `hash(a)` must equal `hash(b)`.

For example:

```python
a = 10
b = 10

print(a == b)          # True
print(hash(a) == hash(b))  # True
```

This consistency is necessary so that dictionary lookup works correctly.

However, the reverse is **not** required:

> Equal hash values do not necessarily mean that two objects are equal.

Different objects can have the same hash value. This is called a **hash collision**, and dictionaries have mechanisms to handle collisions.

---

## 7. Hashable Does Not Simply Mean Immutable

A common interview mistake is saying:

> "All immutable objects are hashable."

This is not the best definition.

The correct concept is:

> **Hashable means an object has a hash value that remains stable during its lifetime and has compatible equality behavior.**

Many immutable built-in types are hashable:

```text
int
float
str
bytes
frozenset
tuple (if all elements are hashable)
```

But hashability should be treated as its own property rather than simply as a synonym for immutability.

You can check it directly:

```python
hash(obj)
```

If the object is not hashable, Python raises:

```text
TypeError: unhashable type: ...
```

---

## 8. Why This Matters Beyond Dictionaries

Hashability is also important for **sets**.

A set is also hash-table-based:

```python
s = {10, 20, 30}
```

Therefore, set elements must also be hashable.

For example:

```python
s = {[1, 2, 3]}
```

fails because a list is unhashable.

But:

```python
s = {(1, 2, 3)}
```

works because the tuple is hashable.

So the rule applies to both:

```text
Dictionary → keys must be hashable
Set        → elements must be hashable
```

---

## 9. Simple Real-World Analogy

Think of a dictionary like a library's organized storage system.

A key is used to determine where an item should be stored:

```text
Key
 ↓
Hash
 ↓
Storage location
```

If the key could change after being stored, the system could no longer reliably determine where the item belongs.

Therefore, the key needs a **stable identity for hashing**.

---

## Common Mistakes

### Mistake 1: "Keys must be immutable."

More precise:

> Keys must be **hashable**. Many immutable objects are hashable, but hashability is the actual requirement.

### Mistake 2: "Different keys must have different hashes."

False.

Two different keys can have the same hash value. Dictionaries handle such **hash collisions**.

### Mistake 3: "A tuple is always hashable."

False.

```python
([1, 2], 3)
```

is a tuple, but it is not hashable because it contains a list.

---

## Interview Takeaway

> **Dictionary keys must be hashable because dictionaries use hashing to efficiently locate keys in a hash table. A key's hash must remain stable while it is used as a key, and objects that compare equal must have equal hashes. This is why mutable objects such as lists and dictionaries cannot normally be dictionary keys, while hashable objects such as strings, integers, and suitable tuples can be used as keys.**
