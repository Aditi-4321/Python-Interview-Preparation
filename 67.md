# Question 67 — When would you use multiprocessing?

## Answer

I would use **multiprocessing** when I have a **CPU-bound workload** that can be divided into relatively independent tasks and I want to use multiple CPU cores.

The basic idea is:

> **Use multiprocessing when computation is the bottleneck and the work can benefit from running in separate processes.**

Each process has its own Python interpreter and memory space, so suitable CPU-bound Python code can execute in parallel across multiple CPU cores.

---

## 1. When is multiprocessing useful?

Multiprocessing is particularly useful when:

* The task is **CPU-bound**.
* The work can be divided into independent tasks.
* Each task is large enough to justify process overhead.
* Multiple CPU cores are available.
* The workload spends significant time executing Python-level computation.

For example:

```text
Large dataset
      ↓
Split into independent chunks
      ↓
Process 1 → Chunk 1
Process 2 → Chunk 2
Process 3 → Chunk 3
Process 4 → Chunk 4
      ↓
Combine results
```

---

## 2. Example: CPU-intensive calculation

Suppose we need to perform an expensive calculation for many independent inputs:

```python id="y2p6g1"
from multiprocessing import Pool

def square(x):
    return x * x

if __name__ == "__main__":
    numbers = range(1_000_000)

    with Pool() as pool:
        results = pool.map(square, numbers)
```

Here, multiple worker processes can process different parts of the workload.

### Why can this help?

In traditional GIL-enabled CPython, multiple threads cannot execute Python bytecode simultaneously within the same process.

Multiprocessing creates separate processes:

```text
Process 1 → GIL 1 → CPU Core 1
Process 2 → GIL 2 → CPU Core 2
Process 3 → GIL 3 → CPU Core 3
Process 4 → GIL 4 → CPU Core 4
```

This allows suitable CPU-bound work to execute in parallel.

# 3. Common use cases

### A. CPU-heavy data processing

For example:

```text
Large dataset
      ↓
CPU-intensive transformation
      ↓
Multiple independent chunks
```

Multiprocessing can process different chunks concurrently.

### B. Image processing

If thousands of images require CPU-intensive transformations:

```text
Images
  ↓
┌─────────┬─────────┬─────────┐
Process 1 Process 2 Process 3
  ↓         ↓         ↓
Images    Images    Images
```

This can improve throughput when the processing is genuinely CPU-bound.

### C. Scientific computation

Independent mathematical calculations can sometimes be distributed across processes.

### D. Batch ML preprocessing

Suppose preprocessing each record or image is computationally expensive and independent.

You can divide the data into batches and process those batches using multiple worker processes.

### E. Running independent jobs

If you have multiple independent CPU-heavy jobs:

```text
Job A → Process 1
Job B → Process 2
Job C → Process 3
Job D → Process 4
```

multiprocessing can execute them concurrently.

---

# 4. When would you NOT use multiprocessing?

Multiprocessing is not automatically the best solution.

### I/O-bound tasks

If the program mostly waits for:

* Network responses
* APIs
* Database queries
* File I/O

then **threading or `asyncio`** may be more appropriate.

```text
I/O-bound → Threading / asyncio
CPU-bound → Multiprocessing / optimized native code
```

### Very small tasks

Creating processes and communicating between them has overhead.

If the work is tiny:

```text
Task computation: 1 ms
Process overhead: 5 ms
```

multiprocessing could actually make the program slower.

### Large amounts of shared data

Processes have separate memory spaces.

If every task needs to exchange huge amounts of data, serialization and inter-process communication can become expensive.

---

# 5. Important multiprocessing overhead

Multiprocessing has costs such as:

* Creating processes
* Scheduling work
* Serializing data
* Inter-process communication
* Combining results
* Additional memory usage

For example:

```text
Parent Process
     │
     ├── send data ──> Worker
     │
     ├── send data ──> Worker
     │
     └── collect results
```

If the amount of computation is small compared with this overhead, multiprocessing may not provide a benefit.

# 6. Multiprocessing in AI/ML

Consider an image-processing pipeline:

```text
10,000 Images
       ↓
CPU-intensive preprocessing
       ↓
Resize
Normalize
Feature extraction
       ↓
Training dataset
```

If preprocessing is CPU-bound, we could distribute the work:

```text
             Images
                ↓
       ┌────────┼────────┐
       ↓        ↓        ↓
   Process 1 Process 2 Process 3
       ↓        ↓        ↓
    Batch 1   Batch 2   Batch 3
       └────────┼────────┘
                ↓
         Combined dataset
```

However, if the actual computation is already performed efficiently by NumPy, PyTorch, or another native library, adding Python processes may not always help. We should **profile first**.

---

# 7. Multiprocessing vs Threading

| Situation                       | Usually consider               |
| ------------------------------- | ------------------------------ |
| CPU-bound Python computation    | Multiprocessing                |
| Network requests                | Threading / `asyncio`          |
| Database I/O                    | Threading / `asyncio`          |
| File I/O                        | Threading / `asyncio`          |
| Independent CPU-heavy jobs      | Multiprocessing                |
| Vectorized numerical operations | NumPy/native libraries         |
| GPU-based ML computation        | GPU frameworks such as PyTorch |

These are guidelines, not absolute rules. The correct choice depends on the workload and profiling results.

# 8. Important Python detail: `if __name__ == "__main__"`

When using multiprocessing, especially on platforms that use the **spawn** start method, protect process-starting code with:

```python id="d8a1xa"
if __name__ == "__main__":
    ...
```

For example:

```python id="s4w9c2"
from multiprocessing import Process

def work():
    print("Working...")

if __name__ == "__main__":
    p = Process(target=work)
    p.start()
    p.join()
```

This prevents child processes from unintentionally executing the process-creation code again.

# 9. A practical decision process

When I encounter a slow Python program, I would not immediately choose multiprocessing.

I would follow:

```text
Program is slow
      ↓
Measure and profile
      ↓
What is the bottleneck?
      ↓
   ┌──┴───────────┐
   ↓              ↓
 CPU-bound      I/O-bound
   ↓              ↓
Algorithm/      Threading /
data structure  asyncio / batching
   ↓
Can the work be parallelized?
   ↓
Yes
   ↓
Multiprocessing / native parallelism
   ↓
Measure again
```

---

## Common Mistakes

* ❌ Using multiprocessing just because the program is slow.
* ❌ Using it for I/O-bound tasks without considering simpler concurrency options.
* ❌ Ignoring process communication and serialization costs.
* ❌ Assuming more processes always means better performance.
* ❌ Forgetting the `if __name__ == "__main__":` guard where appropriate.
* ❌ Ignoring libraries that already use efficient native or parallel implementations.

## Interview Follow-up

**Q: Why use multiprocessing instead of threading for CPU-bound Python code?**

> In traditional GIL-enabled CPython, separate processes can execute Python code in parallel across CPU cores, while threads are restricted from simultaneously executing Python bytecode within the same process.

**Q: What is the biggest disadvantage of multiprocessing?**

> Higher overhead and separate memory spaces, which can make process creation and data communication expensive.

**Q: How do you decide whether multiprocessing will actually help?**

> I would profile the application first and check whether the workload is CPU-bound, sufficiently large, and parallelizable enough to overcome multiprocessing overhead.

## Interview Takeaway

> **I would use multiprocessing for sufficiently large, CPU-bound, and parallelizable workloads where multiple CPU cores can provide a real benefit. I would avoid it for tiny tasks or primarily I/O-bound workloads where threading or `asyncio` may be more appropriate.**
